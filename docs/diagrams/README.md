# Диаграммы (draw.io)

Файлы открываются в draw.io (https://app.diagrams.net или приложение diagrams.net): «Файл → Открыть с устройства». Внутри файла несколько страниц, они переключаются вкладками внизу окна. Экспорт в картинку: «Файл → Экспортировать как → PNG/SVG/PDF».

| Файл | Диаграмма | Откуда берётся |
|---|---|---|
| `er.drawio` | ER-диаграмма базы данных: **страница 1 «Основные сущности (для записки)»**: 19 главных таблиц с ключами и несколькими полями, это то, что идёт в раздел 4.1.4. Дальше по странице на каждый модуль (счета и проводки, переводы, вклады, кредиты, карты, платежи, антифрод, ...) | автоматически из работающей базы PostgreSQL |
| `classes.drawio` | диаграммы классов: слои приложения (контроллеры, сервисы, модели), сервисы бизнес-логики и их зависимости, модели доступа к данным, библиотеки | автоматически из исходного кода `src/` |
| `usecases.drawio` | диаграмма вариантов использования: гость, клиент и четыре роли сотрудников | описана в `scripts/uml-drawio.js` |
| `sequence.drawio` | диаграммы последовательности: перевод клиенту банка, заявка на кредит, закрытие операционного дня | описаны в `scripts/uml-drawio.js` |
| `class-diagrams.drawio` | диаграммы классов по образцу учебных (три отсека, кратности, агрегация и композиция): 7 страниц: 4 по предметной области (пользователи и счета, платежи и проводки, вклады, кредиты) и 3 по слою бизнес-логики (закрытие дня, проверка и подтверждение, учёт и уведомления) | `npm run uml:classes` (`scripts/class-diagrams.js`) |
| `views.drawio` | модели представления для раздела 1.5: варианты использования (5), последовательности (2), деятельность (2), состояния (4), компоненты, развёртывание | `npm run uml:views` (`scripts/uml-views.js`) |

## Как перестроить

Диаграммы ER и классов можно пересоздать после любого изменения базы или кода:

```
npm run er:drawio     # ER по базе из DATABASE_URL
npm run uml:drawio    # классы, варианты использования, последовательности
```

Файлы перезаписываются. Если вы вручную поправили расположение в draw.io, сохраните файл под другим именем, иначе правки пропадут.

## ER в MySQL Workbench (если нужен именно такой вид)

MySQL Workbench не умеет подключаться к PostgreSQL, но умеет строить диаграмму из SQL-файла. Для этого есть `er-workbench.sql`: учебная выжимка рабочей схемы на 14 главных таблиц (роли, пользователи, клиенты, счета, документы и проводки, переводы, вклады, кредиты, карты, платежи) с ключами и основными полями, переписанная в диалект MySQL. Рабочая база проекта при этом остаётся в PostgreSQL, файл нужен только для рисования.

1. В Workbench: «File → New Model».
2. «File → Import → Reverse Engineer MySQL Create Script...», выберите `docs/diagrams/er-workbench.sql`, отметьте «Place imported objects on a diagram», нажмите Execute.
3. Откроется EER-диаграмма. Расставьте таблицы мышью (или «Arrange → Autolayout»), при необходимости «Model → Diagram Properties and Size».
4. Экспорт: «File → Export → Export as PNG/SVG/PDF».

### Как расставить таблицы, чтобы не было клубка

Workbench при импорте раскладывает таблицы как попало. Перетащите их по такой схеме (в скобках: с кем связана таблица, соседи рядом):

```
 1-й ряд:   roles ── users ── clients ───────────── deposit_products
 2-й ряд:   loan_products ── loan_applications        accounts ── deposits
 3-й ряд:                    loans              cards    payments    postings
 4-й ряд:                                                 documents ── transfer_intents
```

- Центр схемы: **accounts** (счёт) и **clients**. К счёту ведёт больше всего связей, поэтому его ставят в середину, а таблицы со связью на него (`cards`, `payments`, `postings`, `transfer_intents`, `loans`, `deposits`) вокруг.
- Связанные таблицы ставьте рядом, а не по алфавиту. Правило: длинная линия через чужую таблицу означает, что таблицу нужно подвинуть.
- Таблицу `documents` ставьте рядом с `postings`, `payments` и `transfer_intents`: у всех троих есть связь на неё.
- Одно-два пересечения на такой схеме неизбежны, для курсовой это нормально.
- Включите привязку к сетке («View → Snap to Grid») и подвиньте линии: сегмент связи можно потянуть мышью, чтобы обойти таблицу.
- Лишние связи убираются двойным щелчком по линии (окно связи) или удалением внешнего ключа в таблице. Вторичные связи (`payout_account_id`, `to_account_id`, `initiated_by` и подобные) в этом файле уже убраны.

Файл создаётся командой `npm run er:mysql`. Какие таблицы попадают в него, задаёт список `CORE` в `scripts/er-mysql.js`: уберите или добавьте таблицы, и перезапустите команду.

Остальные таблицы (справочники, сессии, коды, настройки, очередь писем, антифрод, журнал и т. д.) на диаграмму можно не выносить: опишите их в словаре данных таблицей «таблица, назначение, ключевые поля», а полный скрипт приложите как `db/schema.sql`.

## Вид ER-диаграммы

Таблицы нарисованы в стиле MySQL Workbench: синий заголовок, значки столбцов (жёлтый ромб: первичный ключ, красный: внешний ключ, синий: обычное поле, пустой: поле может быть пустым), серая полоса Indexes, связи пунктиром с «вилкой» (ER-нотация «ворона лапка») и прямыми углами.

## Как устроена ER-диаграмма

Скрипт `scripts/er-drawio.js` читает схему так же, как это делают графические клиенты: запрашивает у PostgreSQL системное представление `information_schema` (таблицы, столбцы и типы, первичные ключи, внешние ключи) и рисует из этого файл draw.io. Ключи помечены `PK` и `FK`, связи нарисованы по внешним ключам (на стороне «многие» стоит «вилка»). На странице модуля таблицы соседних модулей показаны серым.

## Что в диаграммах нужно доработать вручную

- Автоматическая раскладка не знает, какие связи важнее. Для плаката перетащите таблицы так, чтобы пересечений было меньше, и уберите лишние поля.
- Для нотации IDEF1X (если её требует руководитель) стили таблиц и связей придётся поменять в draw.io: набор фигур «Entity Relation» есть в левой панели.
- Диаграммы вариантов использования и последовательности описаны текстом в скрипте. Подписи можно править прямо в draw.io.
